# Event Inventory Export (`MOONFORGE_EVENTS.md`)

At the end of verification — after the event inventory is presented in
chat — also **write it to the project as a file**, so it survives after the
conversation ends. This is the same information already gathered for
"Present the event inventory" / "Present Results", saved rather than only
shown once.

## Where

**Project root**, filename `MOONFORGE_EVENTS.md` — same location as
`.moonforge.json`, regardless of platform (web/Unity/Unreal/generic all use
this one location, not a per-engine SDK folder).

## When

Every time `moonforge-verify` runs, **overwrite the file completely** — do
not append, and do not attempt to merge in or preserve manual edits. This is
a generated artifact, owned by the skill, the same way `.moonforge.json` is.
The file's own header says so explicitly (below), so a developer who opens it
knows not to hand-edit it.

## Scope

Cover **every event currently in the project**, not just what this run
touched. Re-scan and re-derive from the actual codebase each time (the same
full-project grep `moonforge-verify` already does for its own event
inventory step) — never diff against a previous run or assume incremental
state. Most real integrations happen incrementally across multiple sessions,
so a partial export would misrepresent what the game actually sends.

## Format

Markdown only. Group by tier, and include every event whether it was
instrumented this run, in an earlier session, or by hand — same rule as
above.

```markdown
<!-- Auto-generated by MoonForge - do not edit by hand. Regenerated on every /moonforge:verify run. -->

# MoonForge Events — <Game Name>

_Last verified: <ISO date>_

## P0 — Core (SDK auto-tracked, no code needed)

| Event | Properties |
|-------|------------|
| `session_start` | `session_id`, `previous_session_id` (on re-engagement) |
| `session_end` | `session_id`, `duration_seconds` |
| `first_open` | — |
| `app_update` | `previous_version` |
| `alias` | `id`, `previous_id` |

## P1 — Must implement

| Event | Trigger | Properties |
|-------|---------|------------|
| `iap_completed` | `Shop.cs:82` | `product_id`, `price`, `currency`, `transaction_id` |
| `tutorial_complete` | `Onboarding.cs:41` | `outcome` |

## P2 — Should implement

| Event | Trigger | Properties |
|-------|---------|------------|

## P3 — Optional

| Event | Trigger | Properties |
|-------|---------|------------|
```

- P0 rows have no `Trigger` column value (they're SDK-internal, not a call
  site in game code) — use a two-column table for P0, three columns
  (`Event`/`Trigger`/`Properties`) for P1–P3.
- **Build the P0 table by copying `moonforge-events/references/telemetry-model.md`'s
  row set directly, not by reconstructing it from what's visible in game
  code.** `alias` in particular has no call site to grep for at all — it
  fires inside `identify()`'s own implementation, not as its own tracking
  call — so an inventory built by pattern-matching what got called drops it
  every time. This is exactly the mistake that produced a `MOONFORGE_EVENTS.md`
  missing `alias` in the field; source the P0 rows from the model doc, always.
- `Trigger` is `file:line` when discoverable from the grep already done for
  the chat presentation; if a platform's inventory step doesn't resolve line
  numbers (e.g. a minified bundle), use the file path alone rather than
  omitting the column.
- Omit a tier's table entirely if nothing in the project falls into it,
  rather than showing an empty table with just a header row.
- Locked events (revenue/economy/FTUE/accounts) use the exact names/props
  from `moonforge-events/references/telemetry-model.md`; game actions and P3
  engagement events use whatever the project actually calls them.

## Regenerating on uninstall

Not this skill's job — see `moonforge-uninstall`, which deletes
`MOONFORGE_EVENTS.md` in the same step it deletes `.moonforge.json`. A file
describing events that no longer exist is actively misleading, not just
clutter.
